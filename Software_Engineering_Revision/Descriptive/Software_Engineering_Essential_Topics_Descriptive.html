1. System Design (HLD & LLD)

Horizontal vs Vertical Scaling

Vertical Scaling (Scale Up) Horizontal Scaling (Scale Out)
Add more power to existing machine (CPU, RAM) Add more machines to the pool
Limited by hardware capacity Virtually unlimited scaling
Single point of failure Built-in redundancy
Simpler to implement Requires distributed system design
Expensive high-end hardware Use commodity hardware
🌍 Real-World Example

Vertical: Your database server is slow. You upgrade from 16GB RAM to 64GB RAM and add more CPU cores.

Horizontal: Your web servers can't handle traffic. Instead of one big server, you use 10 smaller servers behind a load balancer.

Load Balancing

Load balancers distribute incoming traffic across multiple servers to ensure no single server is overwhelmed.

Load Balancing Algorithms

  • Round Robin: Requests go to servers in rotation (1, 2, 3, 1, 2, 3...)
  • Weighted Round Robin: Stronger servers get more requests
  • Least Connections: Route to server with fewest active connections
  • IP Hash: Same client IP always goes to same server (session affinity)
  • Least Response Time: Route to fastest responding server

L4 vs L7 Load Balancing

L4 (Transport Layer) L7 (Application Layer)
Works with TCP/UDP packets Works with HTTP/HTTPS content
Faster, less overhead Slower but smarter routing
Cannot inspect content Can route based on URL, headers, cookies
🌍 Real-World Example: E-commerce Site

L7 load balancer routes /api/* to API servers, /images/* to CDN, and /checkout/* to high-security payment servers - all based on URL path.

Caching Strategies

Caching stores frequently accessed data in fast storage (memory) to reduce database load and improve response times.

Cache Update Strategies

  • Cache-Aside (Lazy Loading): Application checks cache first. On miss, loads from DB and populates cache. Most common pattern.
  • Write-Through: Write to cache and DB simultaneously. Ensures consistency, adds write latency.
  • Write-Back (Write-Behind): Write to cache only, async write to DB later. Fast writes, risk of data loss.
  • Read-Through: Cache sits between app and DB. Cache fetches data on miss automatically.
Cache-Aside Pattern:

  App → Cache (hit?) → Return data
   ↓
  (miss)
   ↓
  App → Database → Update Cache → Return data
🌍 Real-World Example: Twitter Timeline

Your home timeline is cached. When you refresh, Twitter checks cache first (fast). Only on cache miss does it query the database to build your timeline (slow).

Redis vs Memcached: Redis supports data structures (lists, sets, sorted sets, hashes), persistence, and pub/sub. Memcached is simpler, purely in-memory key-value. Use Redis for complex caching needs, Memcached for simple session caching.

Database Sharding & Partitioning

Partitioning (within single database)

  • Horizontal Partitioning: Split rows across tables (orders_2023, orders_2024)
  • Vertical Partitioning: Split columns (frequently vs rarely accessed)

Sharding (across multiple databases)

Distributes data across multiple database servers. Each shard holds a subset of data.

Sharding Strategy How It Works Pros/Cons
Range-based User IDs 1-1M on Shard1, 1M-2M on Shard2 Simple, but can cause hotspots
Hash-based shard = hash(user_id) % num_shards Even distribution, hard to add shards
Directory-based Lookup table maps key to shard Flexible, lookup overhead
🌍 Real-World Example: Instagram

Instagram shards user data by user_id. When you view someone's profile, the system knows exactly which shard to query based on their user_id hash.

CAP Theorem

In a distributed system, you can only guarantee two of three properties:

  • Consistency: Every read receives the most recent write
  • Availability: Every request receives a response (success or failure)
  • Partition Tolerance: System continues operating despite network failures
Since network partitions are unavoidable in distributed systems, you must choose between CP (consistency + partition tolerance) or AP (availability + partition tolerance).
System Type Choice Example
Banking System CP Better to reject transaction than show wrong balance
Social Media Feed AP OK to show slightly stale data, must always respond

Consistency Models

  • Strong Consistency: All nodes see the same data at the same time
  • Eventual Consistency: All nodes will eventually have the same data, but reads might be stale

Microservices vs Monolithic Architecture

Monolithic Microservices
Single deployable unit Multiple independent services
Shared database Each service owns its data
Simple to develop initially Complex infrastructure needed
Hard to scale individual components Scale services independently
One technology stack Different tech per service
🌍 Real-World Example: Netflix

Netflix has 700+ microservices: one for recommendations, one for streaming, one for user profiles, one for billing. If the recommendation service fails, you can still watch videos.

Message Queues

Message queues enable asynchronous communication between services, decoupling producers from consumers.

Kafka RabbitMQ
Distributed log-based Traditional message broker
Messages persisted, replayable Messages deleted after consumption
High throughput (millions/sec) Lower throughput, more features
Event streaming, logs, analytics Task queues, request-response
🌍 Real-World Example: Order Processing

When you place an order: OrderService publishes to queue. PaymentService, InventoryService, NotificationService each consume the message independently. If one is down, others still work.

Rate Limiting & Throttling

Protects services from abuse and ensures fair resource usage.

Common Algorithms

  • Token Bucket: Tokens added at fixed rate. Request uses a token. No token = rate limited.
  • Leaky Bucket: Requests enter bucket, processed at fixed rate. Overflow is rejected.
  • Fixed Window: Count requests in fixed time windows (e.g., 100 req/minute).
  • Sliding Window: Rolling count over the past N seconds.
🌍 Real-World Example: Twitter API

Twitter allows 300 tweets per 3-hour window per user. This prevents spam bots from overwhelming the platform while allowing normal users to tweet freely.

2. Clean Code, Architecture & Design Patterns

SOLID Principles

S - Single Responsibility Principle

A class should have only one reason to change - one job, one responsibility.

🌍 Real-World Example

Bad: UserService handles login, sends emails, generates reports, and validates data.
Good: AuthService handles login, EmailService sends emails, ReportService generates reports.

O - Open/Closed Principle

Software entities should be open for extension but closed for modification. Add new features without changing existing code.

// Bad: Modify method every time you add a new payment type
class PaymentProcessor {
    process(payment) {
        if (payment.type === 'credit') { ... }
        else if (payment.type === 'paypal') { ... }
        else if (payment.type === 'crypto') { ... }  // Keep adding
    }
}

// Good: Add new payment types without changing existing code
interface PaymentStrategy {
    process(payment): void;
}
class CreditCardPayment implements PaymentStrategy { ... }
class PayPalPayment implements PaymentStrategy { ... }
class CryptoPayment implements PaymentStrategy { ... }  // Just add new class

L - Liskov Substitution Principle

Subclasses should be substitutable for their base classes without breaking the program.

🌍 Real-World Example

Violation: Square extends Rectangle, but setWidth() breaks because Square must keep width=height. A Square cannot fully substitute a Rectangle.

I - Interface Segregation Principle

Clients should not be forced to depend on interfaces they don't use. Split large interfaces into smaller, specific ones.

// Bad: Fat interface
interface Worker {
    work();
    eat();
    sleep();
}
// Robot doesn't eat or sleep!

// Good: Segregated interfaces
interface Workable { work(); }
interface Eatable { eat(); }
interface Sleepable { sleep(); }

class Robot implements Workable { ... }
class Human implements Workable, Eatable, Sleepable { ... }

D - Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions.

// Bad: High-level depends on low-level
class OrderService {
    private MySQLDatabase db = new MySQLDatabase();  // Tightly coupled
}

// Good: Depend on abstraction
class OrderService {
    private Database db;  // Interface
    
    OrderService(Database db) {
        this.db = db;  // Inject dependency
    }
}
// Can use MySQL, PostgreSQL, MongoDB - any implementation

Design Patterns Overview

Creational Patterns

  • Singleton: One instance globally (database connection pool)
  • Factory: Create objects without specifying exact class (document creator)
  • Builder: Construct complex objects step by step (SQL query builder)
  • Prototype: Clone existing objects (game character presets)

Structural Patterns

  • Adapter: Convert interface to match another (power adapter)
  • Decorator: Add behavior dynamically (coffee with extras)
  • Facade: Simple interface to complex system (home theater remote)
  • Proxy: Placeholder for another object (image lazy loading)

Behavioral Patterns

  • Observer: Notify subscribers of changes (newsletter)
  • Strategy: Interchangeable algorithms (sorting strategies)
  • Template Method: Define skeleton, subclasses fill details (data export formats)
  • Chain of Responsibility: Pass request through handler chain (middleware)

Domain-Driven Design (DDD) Basics

  • Entity: Object with unique identity that persists over time (User, Order)
  • Value Object: Immutable object defined by attributes, no identity (Money, Address)
  • Aggregate: Cluster of entities treated as unit, one root entity (Order + OrderItems)
  • Repository: Abstraction for data access (UserRepository)
  • Domain Service: Business logic that doesn't belong to entities
🌍 Real-World Example: E-commerce Order

Order (Aggregate Root): Contains OrderItems (entities within aggregate).
Money (Value Object): $99.99 - no identity, just a value.
You can only access OrderItems through Order, never directly.

Hexagonal Architecture (Clean Architecture)

Separates business logic from external concerns (database, UI, frameworks).

        ┌─────────────────────────────────┐
        │          Frameworks &           │
        │    External Systems (Web, DB)   │
        │  ┌───────────────────────────┐  │
        │  │      Interface Adapters   │  │
        │  │   (Controllers, Repos)    │  │
        │  │  ┌─────────────────────┐  │  │
        │  │  │   Application Layer │  │  │
        │  │  │    (Use Cases)      │  │  │
        │  │  │  ┌───────────────┐  │  │  │
        │  │  │  │ Domain Layer  │  │  │  │
        │  │  │  │ (Entities,    │  │  │  │
        │  │  │  │  Value Objects)│  │  │  │
        │  │  │  └───────────────┘  │  │  │
        │  │  └─────────────────────┘  │  │
        │  └───────────────────────────┘  │
        └─────────────────────────────────┘
        
  Dependency Rule: Inner layers know nothing about outer layers.
Key Benefit: Your business logic (center) doesn't depend on frameworks, databases, or UI. You can swap PostgreSQL for MongoDB, or web UI for CLI, without changing business rules.

3. Databases

ACID Properties

  • Atomicity: All operations succeed or all fail (all or nothing)
  • Consistency: Database moves from one valid state to another
  • Isolation: Concurrent transactions don't interfere
  • Durability: Committed data survives system failures

Isolation Levels

Level Dirty Read Non-Repeatable Read Phantom Read
Read Uncommitted Yes Yes Yes
Read Committed No Yes Yes
Repeatable Read No No Yes
Serializable No No No
🌍 Real-World Example: Bank Transfer

Dirty Read: You see $1000 transferred to your account, but the sender's transaction is rolled back.
Non-Repeatable Read: You read balance as $500, read again, it's $300 (someone withdrew).
Phantom Read: Count transactions shows 10, count again shows 12 (new rows appeared).

Indexing

Indexes speed up data retrieval at the cost of slower writes and storage space.

Index Types

  • B-Tree Index: Default. Good for equality and range queries. Most versatile.
  • B+ Tree Index: Leaf nodes linked. Better for range scans. Used by most databases.
  • Hash Index: Only equality comparisons. O(1) lookup. No range queries.
  • Composite Index: Multiple columns. Order matters! (last_name, first_name)
Composite Index Order: Index on (a, b, c) can be used for queries on (a), (a, b), or (a, b, c), but NOT (b, c) alone. Put most selective columns first.
🌍 Real-World Example: Phone Book

A phone book is indexed by last name. Finding "Smith" is fast. Finding everyone named "John" requires scanning the whole book (no index on first name).

SQL vs NoSQL

SQL (Relational) NoSQL
Structured schema Flexible schema
ACID transactions Eventual consistency (usually)
Complex joins Denormalized, less joining
Vertical scaling typically Horizontal scaling built-in
PostgreSQL, MySQL MongoDB, Cassandra, Redis

When to Choose What

  • Use SQL: Complex queries, transactions, data integrity critical (banking, inventory)
  • Use MongoDB: Flexible schema, document-oriented, rapid development (content management)
  • Use Cassandra: Write-heavy, high availability, time-series data (IoT, logging)
  • Use Redis: Caching, sessions, real-time features (leaderboards, pub/sub)

Optimistic vs Pessimistic Locking

Pessimistic Locking Optimistic Locking
Lock record before reading No locks during read
Prevents conflicts Detects conflicts at commit
SELECT FOR UPDATE Version column comparison
High contention scenarios Low contention scenarios
Risk of deadlocks Risk of retry storms 
-- Optimistic Locking with version column
UPDATE products 
SET quantity = 5, version = version + 1 
WHERE id = 123 AND version = 7;

-- If 0 rows affected, someone else updated it first → retry

4. Data Structures & Algorithms

Big O Notation Reference

Complexity Name Example

O(log n) Logarithmic Binary search

O(n log n) Linearithmic Merge sort, quick sort (average)
O(n²) Quadratic Bubble sort, nested loops

Hash Tables & Collision Handling

Hash tables provide O(1) average case for insert, delete, and lookup.

Collision Resolution

  • Chaining: Store colliding elements in a linked list at same bucket
  • Open Addressing: Find another slot (linear probing, quadratic probing, double hashing)
🌍 Real-World Example

Dictionary (HashMap) in programming: keys are hashed to determine where to store values. Good hash function = uniform distribution = fewer collisions.

Trees

Binary Search Tree (BST)

Left child < parent < right child. O(log n) operations when balanced.

Self-Balancing Trees

  • AVL Tree: Strictly balanced (height difference ≤ 1). More rotations, faster lookup.
  • Red-Black Tree: Loosely balanced. Fewer rotations, used in TreeMap/TreeSet.

Tries (Prefix Trees)

Used for efficient string operations like autocomplete and spell check.

🌍 Real-World Example: Autocomplete

When you type "app" in a search box, a Trie efficiently finds all words starting with "app": apple, application, approach, etc.

Graph Traversals

BFS (Breadth-First Search) DFS (Depth-First Search)
Uses Queue Uses Stack (or recursion)
Explores level by level Explores as deep as possible first
Shortest path (unweighted) Cycle detection, topological sort
More memory for wide graphs More memory for deep graphs
🌍 Real-World Example

BFS: Finding shortest path in Google Maps (nodes = intersections, edges = roads).
DFS: Solving a maze (go deep, backtrack when stuck).

5. Distributed Systems Concepts

Consensus Algorithms

How distributed nodes agree on a single value despite failures.

Raft (Easier to understand than Paxos)

  1. Leader Election: One node becomes leader
  2. Log Replication: Leader replicates commands to followers
  3. Safety: Only log entries from leader with majority support are committed
🌍 Real-World Example: Distributed Database

CockroachDB uses Raft to ensure all replicas agree on the order of transactions. If leader dies, a new one is elected automatically.

Circuit Breaker Pattern

Prevents cascading failures by stopping requests to a failing service.

States

  • Closed: Normal operation, requests pass through
  • Open: Service failing, requests fail immediately (fast fail)
  • Half-Open: Test if service recovered, allow limited requests
    ┌─────────── Failure threshold reached ───────────┐
    │                                                 │
    ▼                                                 │
┌────────┐                                       ┌────────┐
│ CLOSED │ ─────── Success ───────────────────── │  OPEN  │
└────────┘                                       └────────┘
    ▲                                                 │
    │                                                 │
    └────────────── Test request succeeds ────────────┘
                         (Half-Open)
🌍 Real-World Example: Payment Service

If payment service is down, circuit breaker opens. Instead of waiting/timing out for each order, fail immediately and show "Try again later" - better user experience, less load on struggling service.

Idempotency

An operation is idempotent if executing it multiple times has the same effect as executing it once.

HTTP Method Idempotent? Example
GET Yes Get user profile
PUT Yes Update user to specific state
DELETE Yes Delete user (2nd delete = already deleted)
POST No Create order (2nd post = duplicate order)
Making POST idempotent: Use idempotency keys. Client sends unique ID with request. Server checks if ID was processed before. If yes, return cached response instead of processing again.
🌍 Real-World Example: Payment Retry

User clicks "Pay" but network is flaky. Request might be sent twice. With idempotency key, the second request sees "already processed" and returns the original result - no double charge.

Authentication: OAuth 2.0 & JWT

OAuth 2.0 Flow (Authorization Code)

  1. User clicks "Login with Google"
  2. Redirect to Google login page
  3. User logs in, grants permission
  4. Google redirects back with authorization code
  5. Your server exchanges code for access token
  6. Your server uses token to access user's Google data

JWT (JSON Web Token)

Self-contained token with three parts: Header.Payload.Signature

// JWT Structure
{
  "header": { "alg": "HS256", "typ": "JWT" },
  "payload": { "user_id": 123, "role": "admin", "exp": 1735689600 },
  "signature": "HMACSHA256(base64(header) + '.' + base64(payload), secret)"
}

// Token: eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoxMjN9.abc123signature
JWT Benefits: Stateless (no server session storage), contains user info (no DB lookup needed). But: Cannot be revoked until expiry (use short expiry + refresh tokens).

OWASP Top 10 Security Vulnerabilities

1. SQL Injection

// Vulnerable
query = "SELECT * FROM users WHERE id = " + user_input
// Input: "1; DROP TABLE users;" 💀

// Safe - Use parameterized queries
query = "SELECT * FROM users WHERE id = ?"
execute(query, [user_input])

2. Cross-Site Scripting (XSS)

Attacker injects malicious script that runs in victim's browser.

// Vulnerable: User enters this as their name


// Prevention: Escape output, use Content Security Policy
<script>...</script>  // Rendered as text, not executed

3. Cross-Site Request Forgery (CSRF)

Attacker tricks user into performing unwanted action on a site where they're authenticated.

Prevention: CSRF tokens, SameSite cookies, verify Origin header.

🌍 Real-World Example: CSRF Attack

You're logged into your bank. Attacker sends you an email with hidden image: <img src="http://bank.com/transfer?to=attacker&amount=1000">. Your browser sends the request with your auth cookies!

7. DevOps & Cloud Awareness

CI/CD Pipeline

Continuous Integration / Continuous Deployment automates building, testing, and deploying code.

Code Commit → Build → Unit Tests → Integration Tests → Deploy to Staging → Deploy to Production
     │          │          │              │                  │                    │
     └──────────┴──────────┴──────────────┴──────────────────┴────────────────────┘
                        Automated pipeline (Jenkins, GitHub Actions, GitLab CI)
🌍 Real-World Example

Developer pushes code. Within minutes: tests run, Docker image built, deployed to staging, automated UI tests run, and if all pass, promoted to production. Human intervention only for code review.

Docker Basics

# Dockerfile
FROM python:3.9-slim                    # Base image
WORKDIR /app                            # Set working directory
COPY requirements.txt .                 # Copy dependency file
RUN pip install -r requirements.txt     # Install dependencies
COPY . .                                # Copy application code
EXPOSE 8000                             # Document port
CMD ["python", "app.py"]                # Run command

# Build and run
docker build -t myapp:v1 .
docker run -p 8000:8000 myapp:v1

Key Concepts

  • Image: Immutable template (like a class)
  • Container: Running instance of an image (like an object)
  • Registry: Where images are stored (Docker Hub, ECR)
  • Volume: Persistent storage that survives container restart

Kubernetes Basics

Core Components

  • Pod: Smallest deployable unit. One or more containers.
  • Service: Stable network endpoint to access pods.
  • Deployment: Manages pod replicas, rolling updates.
  • ConfigMap/Secret: Configuration and sensitive data.
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3                    # Run 3 instances
  selector:
    matchLabels:
      app: myapp
  template:
    spec:
      containers:
      - name: myapp
        image: myapp:v1
        ports:
        - containerPort: 8000
        resources:
          limits:
            cpu: "500m"
            memory: "256Mi"
🌍 Real-World Example

You deploy 3 replicas of your API. Kubernetes ensures 3 are always running. If one crashes, it automatically starts a new one. If you deploy a new version, it gradually replaces old pods (rolling update).

Observability: Logs, Metrics, Traces

Pillar What Tools
Logs Discrete events (errors, requests) ELK Stack, Splunk, Loki
Metrics Numerical measurements over time Prometheus, Grafana, DataDog
Traces Request flow across services Jaeger, Zipkin, AWS X-Ray
Why all three? Metrics tell you something is wrong (high latency). Logs tell you what went wrong (error message). Traces tell you where it went wrong (which service in the chain).

8. Soft Skills & Behavioral

System Design Interview Approach

  1. Clarify Requirements (2-3 min): Functional & non-functional requirements. Scale, latency, availability targets.
  2. High-Level Design (5-10 min): Draw main components. Data flow. API design.
  3. Deep Dive (15-20 min): Database schema. Scaling strategies. Handle edge cases.
  4. Wrap Up (5 min): Trade-offs discussed. Future improvements. Monitoring strategy.
Common Mistake: Jumping into solution without understanding requirements. Always ask: How many users? Read-heavy or write-heavy? What's acceptable latency? Is data consistency critical?

Code Review Best Practices

As a Reviewer

  • Focus on logic, not style (use linters for style)
  • Ask questions instead of making demands: "What happens if X is null?"
  • Acknowledge good code: "Nice use of the Strategy pattern here!"
  • Prioritize feedback: security > bugs > design > nits

As an Author

  • Keep PRs small and focused (< 400 lines ideally)
  • Write good descriptions explaining WHY, not just WHAT
  • Don't take feedback personally
  • Be open to different approaches
